# 2026-09-29 13:35 — Fix empty SPA pages + 502 on `api.aisztens.hu/api`

## What was broken

User reported two visible symptoms when reaching the production droplet from a
PC browser / Postman:

1. `https://admin.aisztens.hu/` and `https://web.aisztens.hu/` returned an
   HTTP 200 response with **`content-length: 0`** (a completely empty page).
2. `https://api.aisztens.hu/api` returned **HTTP 502**.

SSH / droplet were fine. All four containers (`api`, `postgres`, `caddy`,
`monitor`) were `Up 14 hours`, the `api` healthcheck was `healthy`, the
dist folders were physically present on the host and bind-mounted into
the Caddy container, the rendered Caddyfile had literal hostnames (no
`{env.DOMAIN}` placeholder), and Let's Encrypt certificates existed on
disk. So the cause was code-level, not infra.

## Root cause (two independent code bugs)

### Bug A — Caddy served no SPA body (`content-length: 0`)

[`infra/caddy/Caddyfile`](../../infra/caddy/Caddyfile) `web.<DOMAIN>` and
`admin.<DOMAIN>` blocks declared `root *`, `try_files {path} /index.html`,
and a `handle /api/*` block. In Caddy's Caddyfile-to-JSON adapter, the
presence of **any `handle` block inside a site block disables the
implicit `file_server` that would otherwise be inserted automatically**.
The `try_files` directive becomes a pure matcher + URI rewriter, but
with no `file_server` to actually serve the rewritten URI, the request
falls through to an empty default 200 response.

`caddy adapt --config /etc/caddy/Caddyfile --pretty` confirmed the gap:
the adapted JSON contained `vars`, `rewrite`, `encode`, and
`reverse_proxy` handlers but **no `file_server` handler** for
`admin.aisztens.hu` or `web.aisztens.hu`.

Fix: add an explicit `file_server` directive after each `try_files` in
both blocks. `try_files` then rewrites the URI to the existing file
path (or `/index.html` as the SPA fallback), and `file_server` serves it.

### Bug B — `502` on `api.aisztens.hu/api`

[`apps/api/src/main.ts`](../../apps/api/src/main.ts) called
`await app.listen(process.env.PORT ?? 3000)` without an explicit host
argument. With `@nestjs/platform-fastify`, `listen(port)` with no host
defaults to a **loopback-only bind** (`127.0.0.1` / `[::1]`).

`/proc/net/tcp` inside the running api container showed:

```
sl  local_address rem_address   st ...
 0: 0100007F:0BB8 ...   0A ...   (127.0.0.1:3000, LISTEN)
 0: 00000000000000000000000001000000:0BB8 ... (tcp6 [::1]:3000, LISTEN)
```

Caddy, on a sibling container, tried to dial `api:3000` (the container's
bridge IP `172.18.0.3:3000`). Loopback listeners don't accept that, so
Caddy logged `dial tcp 172.18.0.3:3000: connect: connection refused` and
returned `502` to the browser. The Docker healthcheck still passed
because it dials `127.0.0.1:3000` from inside the same container.

Fix: bind explicitly to `0.0.0.0`. After the rebuild, `/proc/net/tcp`
shows `00000000:0BB8` (= `0.0.0.0:3000`) and Caddy reaches the api
successfully.

## Why this was missed earlier

Both bugs are silent on the "is the container up?" checks most operators
use first (`docker ps`, `curl http://localhost:N/` from inside the
container). They only show up at the cross-container / public-HTTPS
boundary, which is exactly where the symptoms appeared.

## Changes applied (live on the droplet, also in repo)

| File | Change |
|---|---|
| [`apps/api/src/main.ts`](../../apps/api/src/main.ts) | `app.listen(port)` → `app.listen(port, '0.0.0.0')`, with a comment explaining the loopback-default trap and pointing at the `/proc/net/tcp` evidence |
| [`infra/caddy/Caddyfile`](../../infra/caddy/Caddyfile) | Added explicit `file_server` after `try_files {path} /index.html` in both the `web.<DOMAIN>` and `admin.<DOMAIN>` blocks |
| [`docs/Specs/Caddy-Reverse-Proxy.md`](../../docs/Specs/Caddy-Reverse-Proxy.md) | Section 4.1 updated to document the `file_server` line in the directive table; "Utolsó frissítés" bumped to 2026-09-29 |
| Droplet (`/opt/aisztens`) | Same two source edits applied; rendered `Caddyfile.rendered` regenerated; `aisztens/api:latest` image rebuilt (7 min on 1-vCPU droplet); `aisztens-caddy-1` and `aisztens-api-1` recreated with `--force-recreate --no-deps` |

The `/healthz` 404 is **a separate, pre-existing bug**: the compiled
`dist/main.js` on the droplet does not contain the `{ exclude: ['healthz'] }`
option of `setGlobalPrefix`, even though the TypeScript source does. The
Docker healthcheck keeps reporting `healthy` for an unrelated reason.
This is outside the scope of this fix and should be investigated
separately (the api container's compiled JS is stale relative to the
source).

3. Add a one-line smoke test to [`scripts/test/lib/20-cross-service.sh`](../../scripts/test/lib/20-cross-service.sh)

   `https://admin.aisztens.hu/` and asserts `size > 0` + `content-type`
   starts with `text/html`. That would have caught Bug A before the
   user noticed it.

   `200`, which would have caught the stale-dist bug.
