# AIS-122 — Quality gates: layer lint, knip, palette and field-error checks enforced in CI

**Date:** 2026-11-02 · **Ticket:** [AIS-122](https://zakzag.atlassian.net/browse/AIS-122) (subtask of AIS-105) · **Plan:** [`2026-11-02--18-25-00-ais-122-quality-gates-plan.md`](../plans/2026-11-02--18-25-00-ais-122-quality-gates-plan.md)

## What was the problem

[`react.coding-standards.md`](../../.roo/rules/react.coding-standards.md:1) declares the layer map
(§0.6, §1, §2) and the token rules (§7) as non-negotiable, but nothing enforced them: a PR that
imported another page's store, wrote `bg-slate-800`, or branched on `error.code` in JSX merged
green. `apps/web` was also still on Tailwind palette utilities, and its `lint` script was
`echo … && exit 0`.

## Findings and decisions worth remembering

- **`dependency-cruiser` resolves the repo's explicit `.js` specifiers natively** (via
  `enhancedResolveOptions.extensions`). The plan's fallback (`extensionAlias`) is **not usable**:
  it is not part of the config schema and the whole config is rejected. `options.tsConfig` was
  dropped as well — an `extends`-ing tsconfig is resolved from the cwd, producing
  `error TS5083: Cannot read file …apps/admin/tsconfig.base.json` and `TS18003`.
- **The positive fixture caught a real modelling bug**: writing `pages/alpha → features/one`
  failed `no-page-to-foreign-feature`, which is correct — a page may import _its own_ feature
  (`features/<page>`), plus `features/api` and `features/error-surface`. The fixture now follows
  that convention, and the rule is proven to discriminate rather than blanket-fail.
- `knip`'s first run was loud (4 unused files, 21 unused exports, 2 unused devDeps). Most were
  "exported for readability, used in the same file" → `ignoreExportsUsedInFile: true`. Only two
  were genuinely dead: the contract barrel and the `DEFAULT_EMIT` alias.
- `tailwindcss` is imported only from CSS, so it must be an `ignoreDependencies` entry.

## pnpm settings migration (follow-up fix, same day)

`pnpm quality` initially died before running anything with
`ERR_PNPM_VERIFY_DEPS_BEFORE_RUN`: _"node_modules are out of sync with your lockfile, and installing
would drop `pnpm.overrides` … because the `pnpm` field in package.json is no longer read by pnpm"_.

Root cause (two parts):

1. **The wrong pnpm installed `node_modules`.** The repo pins `"packageManager": "pnpm@12.16.1"`,
   but the shell's `pnpm` is 9.15.4, so `pnpm add -D -w dependency-cruiser knip` wrote
   `packageManager: pnpm@9.15.4` into `node_modules/.modules.yaml`. pnpm 12 then refuses to run
   scripts against a store written by another major.
2. **`pnpm.overrides` lived in `package.json`.** pnpm ≥11 reads settings only from
   `pnpm-workspace.yaml`; the repo already used the new location for `allowBuilds`, so the override
   was the last setting in the old place — pnpm 12 saw it as "would be dropped".

Fix: move `overrides.light-my-request` into `pnpm-workspace.yaml` (with the original reason kept as a
comment), restore the planned `^16` / `^5` ranges for the two new devDeps, declare `msw: false` in
`allowBuilds` (pnpm 12 fails on _unlisted_ packages with install scripts: `ERR_PNPM_IGNORED_BUILDS`),
and re-install with the pinned pnpm 12 — after which `pnpm install` is a no-op ("Already up to date").

**Residual, not caused by this change:** pnpm 12 enforces a default 24-hour `minimumReleaseAge`
supply-chain policy, and the committed lockfile contains four entries published earlier _today_
(`@tanstack/react-query@5.105.2` + `@tanstack/query-core@5.105.2` at 13:54Z, `strtok3@10.7.0`,
`token-types@6.2.0`). The pre-run install therefore prints `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`
and a "node_modules may be out of sync" warning, but **the scripts still run and pass** (exit 0).
It clears itself after 2026-11-03T13:54Z; until then a deliberate re-install needs
`pnpm install --config.minimumReleaseAge=0`. No policy was relaxed in the repo — that is a security
decision for the owner, not a side effect of this ticket. CI is unaffected today (it pins pnpm 10,
which has no such policy engine).
