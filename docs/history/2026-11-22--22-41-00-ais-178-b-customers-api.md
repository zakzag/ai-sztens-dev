## 2. Decisions that shaped the code

- **`D2` — the repository opens the transaction.** `runInTransaction<T>(work)` keeps `db.transaction`
  out of the service, while `AuditWriter.write` still *requires* the `tx` handle, so an audit row
  cannot land outside the business write.
- **`D6` — number allocation retries once, in a fresh transaction.** `max()` of the month is read
  inside the write transaction; a `23505` on `customers_customer_number_key` aborts that transaction,
  so the whole unit of work is inside the loop, not just the insert.
- **`D7` — an empty `PATCH` short-circuits.** No `UPDATE`, no audit row, the current row returned:
  `updated_at` is `$onUpdate`, so an empty write would bump it and produce a "phantom" change.
- **`D8` — `:id` is validated with the existing `ZodValidationPipe`.** `'abc'::uuid` raises `22P02`
  → `500`; `customerIdSchema` makes it a `400 VALIDATION_FAILED`.
- **`D9` — the four mutating handlers read `@Req()`.** `ip`, `user-agent` and `source` are not in the
  envelope context, and the amended `ReqCtx` docblock says so.

### Deviations from the plan (all deliberate, all documented in code)

1. **The two derived projections are correlated scalar subqueries, not `LATERAL` joins.** Same plan
   class for these shapes (per-row SubPlan on an indexed predicate), one round trip either way, no
   fan-out — and it keeps the page query a single `select … from customers`, which the repository
   spec can assert on. Documented at the top of `customers.repository.ts`.
2. **`toContactsWithRoles` takes the joined rows** (`ContactRoleJoinRow[]`) instead of two arrays, so
   the detail reads contacts **and** their roles in one left join (the "at most four round trips" the
   plan promises).
3. **Write responses are re-read through `findById`.** `UPDATE … RETURNING` cannot compute
   `lastActivityAt` / `primaryContactName`; answering `null` after an edit would lie about a customer
   that has activities. One extra read on the write path buys an accurate payload.
4. **`soft_delete` reads its pre-image first.** The ledger's `before` must be the archived row, not
   the row carrying the archive marker.
