# AIS-14 — what is still missing (code-level gap analysis)

**Date:** 2026-11-23
**Ticket:** AIS-14 `Admin - cég adatbázis` (Story, `To Do`), subtasks AIS-16 / AIS-18 / AIS-177 / AIS-178
**Scope of this analysis:** the **code** only. Docs were read only where they are newer than
2026-11-22 (the AIS-178 plans), because older specs may already be superseded.
**Verdict:** the persistence layer and the six `customers` endpoints are done; everything that
hangs off a customer — client service, contacts, tags, customer users, activities, audit-log read —
is still missing, and the repo's own coverage gate is **red** because of it.

---

Measured against the code today:

| --- | --- | --- |

| Layer | What exists |
| --- | --- |
| Database | `customer.customers/tags/customer_tags/contacts/contact_roles`, `iam.operators/customer_users`, `activity.activities`, `audit.audit_logs` — all enums, partial unique indexes, composite FKs |
| Migrations | `0005` (customer + iam), `0006` (activity + audit), `0007` (append-only triggers + grants) |

| API | the six `customers` operations, one transaction per write, `AuditWriter` in the same transaction, `409 STALE_WRITE`, `409 CUSTOMER_TAX_NUMBER_CONFLICT`, soft delete that frees the tax number |
| Tests | unit specs for guard/logic/mapper/repository/service/controller/module; e2e for the six routes; `audit-immutability.e2e-spec.ts` |

The remaining work is **not** a rewrite: it is four vertical slices that were planned (and lettered)
in `docs/plans/2026-11-22--22-16-00-ais-178-b-customers-api-slice-plan.md` §9 but never shipped.

## 3. The missing pieces, in the order they should be built

### M1 — `packages/api-client/src/customers/` (planned "slice c") — **blocks everything**

**What is missing:** the whole folder. Today there is only `api-keys/` there, and
`createServiceFactories()` returns `{ apiKeys }` only, while `API_ENDPOINTS` already publishes
`customers.list / findById / create / update / updateStatus / remove`.

**Why it is needed:** `packages/api-client/test/service-coverage.test.ts` compares the registry with
the built services. Two of its three gate assertions fail right now (`missing` is not empty, and the
namespace list is `['apiKeys']` instead of `['apiKeys','customers']`), so the DoD's
"`pnpm test` green" cannot be true and `main` is red. It is also the only way the admin UI (AIS-15)
can reach the API at all — no client service, no UI.

**What it must contain:** `customers.service.ts` (6 methods, parse every response with the shared
schemas), `customers.interface.ts`, `customers.const.ts` with paths derived from
`clientPathOf('customers.list')` / `clientPathOf('customers.findById')`, plus the
`service.registry.ts` line `customers: createCustomersService`. One test file per behaviour,
mocking `fetch` (never the network).

> The plan's own rule: **b and c merge together, one PR.** Shipping the API without the client
> service just keeps the red window open.

### M2 — contacts + contact roles (planned "slice d")

**What is missing:** no controller, no service, no repository method, no client method, no registry
entries for
`POST/PATCH/DELETE /api/admin/customers/:id/contacts[/:contactId]` and the role assignments.

**Why it is needed:**
- The `customers` detail response already returns `contacts[].roles`; today nothing can ever fill
  that array, so the AIS-15 contact card would be read-only by construction.
- The DB already enforces "one `primary` contact per customer" (`contact_roles_primary_key`), but
  nobody maps that violation to an error code, so the admin would get a raw `500`.
- `contact_roles` has no `deleted_at` on purpose: a contact soft delete must **delete** its role
  rows, otherwise the `primary` slot stays occupied forever. That rule currently lives nowhere in
  the code.

**Needs also:** `CUSTOMER_PRIMARY_CONTACT_CONFLICT` (`409`) in `error-code.const.ts` +
`API_ERROR_CODE_STATUS` + the Hungarian copy in `apps/admin/src/lib/error-message.const.ts`
(otherwise the admin copy-parity test fails).

### M3 — tags + customer users (planned "slice e")

**What is missing:** `POST /:id/tags` (create a tag and attach), `PATCH /:id/tags` (attach an
existing one), detach; and `POST /:id/customer-users` (invite), `PATCH`/`DELETE` of a user.

**Why it is needed:**
- `customers.tags` and `customers.customerUsers` are already part of the detail payload but are
  always `[]` — the same "read-only by construction" problem as M2.
- `iam.customer_users` carries the "one active `owner` per customer" unique index
  (`customer_users_customer_owner_key`). Without an endpoint and an error code
  (`CUSTOMER_OWNER_CONFLICT`) the second-owner `409` in the DoD cannot exist and cannot be tested.
- The invitation state machine (`invited` → `active`) has no write path, so the fields
  `invitedByOperatorId` / `invitedAt` / `acceptedAt` are dead columns for now.

### M4 — activities + audit-log read (planned "slice f") — **the DoD's e2e chain depends on it**

**What is missing:**
- `GET /:id/activities`, `POST /:id/activities`, `PATCH /:id/activities/:activityId`,
  `DELETE /:id/activities/:activityId`
- `GET /:id/audit-logs` (paginated, read-only)

**Why it is needed:**
- There is no `note` column in the model on purpose (`schema.ts` note, AIS-16 `D9`): **every**
  remark about a customer is an activity row. With no activity endpoint, an operator cannot record a
  single remark about a customer — the central feature of the data model is unreachable.
- `customers.lastActivityAt` is derived from `max(activities.created_at)` and is therefore `null`
  for every customer forever, and the list's `?sort=lastActivityAt` sorts a value that can never
  change.
- The DoD's e2e chain is literally "create → list → detail → **activity** → **appears in the audit
  log**". Half of it cannot be written today.
- The ledger is written but never readable through the API, so the "Napló" tab of AIS-181 has no
  source. `SELECT` is already granted on `audit.audit_logs` exactly for this
  (`0007_audit_immutability.sql`), so only the read path is missing.
- `AUDIT_TABLE_NAMES` already lists `activities` / `contacts` / `contact_roles`, i.e. the writer
  accepts those tables — only the callers are missing.

### M5 — registry entries for the child resources

**What is missing:** `API_ENDPOINTS` currently contains the six `customers` operations only.
`activities`, `contacts`, `customerUsers`, `tags`, `auditLogs` have schemas but no
`operationId` entries.

**Why it is needed:** three gates depend on the registry and they all fail loudly when it drifts:
the OpenAPI document (`/api/openapi.json` is generated from the registry, so unregistered routes are
undocumented), the envelope-contract e2e (a mounted enveloped route that is not registered with the
same verb and path fails), and the AIS-110 coverage gate. The rule is that a registry entry, its
client method and its controller land **together** — so M2–M4 cannot be merged without M5.

### M6 — the two missing `409` error codes (+ admin copy)

`error-code.const.ts` knows `CUSTOMER_NUMBER_CONFLICT` and `CUSTOMER_TAX_NUMBER_CONFLICT` only.
Missing: `CUSTOMER_PRIMARY_CONTACT_CONFLICT`, `CUSTOMER_OWNER_CONFLICT` — with their
`API_ERROR_CODE_STATUS` mapping (`409`) and their Hungarian message in `apps/admin`.

**Why it is needed:** the DoD names those two `409` cases explicitly, and the project convention is
"a conflict is classified by constraint name, never by a pre-check". Without the codes the
constraint violation would surface as `INTERNAL_ERROR` (`500`).

### M7 — test coverage the DoD asks for and that does not exist yet

| DoD case | Today |
| --- | --- |
| duplicate **tax number** → `409` | yes, e2e |
| duplicate **customer number** → `409` | unit only (the retry loop); no e2e — hard to force, acceptable if documented |
| second `owner` → `409` | impossible (no endpoint) |
| second `primary` contact → `409` | impossible (no endpoint) |
| create → list → detail → **activity** → audit row | half missing |
| contact soft delete removes its role rows | impossible (no endpoint) |

**Why it is needed:** these are not "nice to have" extras — they are the riskiest transitions in the
domain (partial unique indexes, cascade behaviour), and they are the only proof that the DB
invariants are mapped to a client-visible answer instead of a `500`.

### M8 — closing paperwork

- `docs/Specs/API-Convention.md`: the `customers` section (six routes + the two extra `409` codes +
  the `admin` audience), header date bumped.
- `docs/Specs/Database-Local.md`: the four schemas, the append-only trigger, the documented purge
  recipe for ledger rows written by the e2e.
- `docs/history/<ts>-…md` change summary for the remaining slices, and the AIS-14 **milestone**
  (it is due when AIS-178 closes — the rules make it mandatory for a change of this size).

### M9 — one DoD sentence contradicts the code convention (needs a recorded decision)

The DoD says `PATCH /:id` answers **`422` semantic error**. The implementation follows the standing
`api-keys` convention (AIS-108): `400 VALIDATION_FAILED` for a malformed body and
`409 STALE_WRITE` for a version mismatch, and an empty PATCH is a silent no-op (`D7`).
Nothing is "missing" here — but **the ticket text must be updated** (or a `422` code must be added to
the catalogue, which would be a one-off in the whole API). Whoever closes AIS-14 should record the
choice; otherwise the next reader will think a `422` branch was forgotten.

### M10 — explicitly out of scope for AIS-14 (track only)

- **Admin UI** (pages, wizard, tabs, feature hooks `use-customers.ts`, `use-customer-contacts.ts`,
  `use-customer-users.ts`, `use-customer-activities.ts`, `use-customer-audit-logs.ts`) — owned by
  **AIS-15** and its subtasks. `apps/admin/src` has no `customers` folder today; that is expected,
  not a gap.
- **Subscriptions / services / modules** — AIS-176.
- **Admin authentication** — the audit actor is `system` until AIS-73/74; ledger rows written in
  this period cannot be backfilled (AIS-177 `D6`). Known limitation, not a defect.

## 4. A small inconsistency worth fixing on the way

- The AIS-178/b plan lists `customers.service.interface.ts`, but the feature has no such file: the
  controller injects the concrete `CustomersService`. The repository and the audit writer **are**
  behind interfaces/tokens; the service is the only concrete dependency. Low risk, but the coding
  standard says "depend on abstractions", so it is either added or the plan is corrected.

## 5. Suggested order and why

```text
M1 api-client service ──► AIS-110 gate green ──► AIS-15 can start
M5 registry entries + M6 error codes ──► M2 contacts ──► M3 tags + users ──► M4 activities + audit read
                                                     └────────► M7 409 / cascade tests ──► AIS-14 DoD
```

1. **M1** first — it is the only item that turns `main` green and it unblocks AIS-15.
2. **M5 + M6** next — the contract must exist before any child controller.
3. **M2 → M3 → M4** — each slice is controller + service + repository + registry + client + tests,
   in that order, because every one of them adds a `409` and an audit row that must be proven.
4. **M7** closes the DoD, **M8/M9** close the paperwork.

contract exposes six operations while the ticket's structure promises activities, audit logs,
contacts, tags and customer users as well.
