## 3. Three production defects the e2e gate found (fixed, `abe89ba` + `41cb669`)

### D-A — `42702 ambiguous column reference` on every customer list request

`GET /api/admin/customers` answered **500** for every call:

```
select "id", … , (select max("created_at") from "activity"."activities"
                  where "customer_id" = "id" and "deleted_at" is null), ( … )
from "customer"."customers" …
```

Root cause: a `sql` template embedding a Drizzle `Column` renders the **bare** column name once the
template becomes a `select()` field (verified against `PgDialect`). In a correlated subquery
`customer.contacts` and `customer.contact_roles` both carry `customer_id`, so Postgres could not
resolve it.

Fix: [`apps/api/src/db/sql-reference.ts`](../../apps/api/src/db/sql-reference.ts:1) —
`qualifiedColumn(table, column)` renders `"schema"."table"."column"` from the Drizzle metadata via
`sql.raw`, which the query builder never rewrites. Both subqueries in
[`customers.repository.ts`](../../apps/api/src/customers/customers.repository.ts:87) use it, and
[`customers.repository.spec.ts`](../../apps/api/src/customers/customers.repository.spec.ts:41)
now asserts the rendered projection stays qualified.

### D-B — `TypeError: value.toISOString is not a function` on `GET /:id`

A derived column (`sql<Date | null>` over a subquery) has no Drizzle decoder, so the driver returns
the **textual** timestamp while the type says `Date`. `toNullableIsoString` trusted the annotation.

Fix: [`iso-date.ts`](../../apps/api/src/common/date/iso-date.ts:26) accepts `Date | string | null`,
parses the string and throws on a value that is neither (instead of producing `Invalid Date`).

### D-C — `statusChangedAt` was 2 ms after `createdAt`

`toNewCustomerRow` wrote `statusChangedAt` from the service clock while `created_at` came from the
DB — two clocks, two values, and the e2e asserts they are equal on a fresh row.

Fix: the insert no longer sends `statusChangedAt`; the column's `now()` default fills it in the same
statement, so both timestamps are identical by construction. `toNewCustomerRow` lost its `now`
parameter.

### D-D — the activity `PATCH` answered 500 with an unhelpful log line

The 5xx line named the statement but not the reason, so the first step was making
[`ApiExceptionFilter`](../../apps/api/src/common/http/api-exception.filter.ts:221) log the `cause`
chain of a 5xx (with a spec covering it). That surfaced the real error:

```text
TypeError: The "string" argument must be of type string or an instance of Buffer or ArrayBuffer.
Received an instance of Date (ERR_INVALID_ARG_TYPE)
```

Root cause: the optimistic-lock guard bound the token as a `Date` inside a raw `sql` chunk
(`coalesce(updated_at, created_at) = ${expectedLastWrite}`). A raw `sql` parameter **bypasses the
column encoder** that `eq()` uses — that encoder is what turns a `Date` into its ISO text — and the
driver then rejects the statement.

Fix: bind `expectedLastWrite.toISOString()` with an explicit `::timestamptz` cast
([`customers-activities.repository.ts`](../../apps/api/src/customers/customers-activities.repository.ts:143)).
The token-only `PATCH` 400 was a cascade of this failure (the *first* edit never happened, so the
token it read was `null`), not a schema defect.

### D-E — `customers.e2e-spec.ts` «timeouts» were load, not a defect

Every test in that suite failed inside `beforeAll` at jest's 5 s hook limit. Run alone the suite
passes in 3 s (14/14). The cause is the default worker pool on this machine, so the gate command is
`--runInBand`; nothing in the suite was changed.

**The audit ledger must be purged between runs.** `customer-contacts` failed with
`countAuditRows(null, 'contact_roles', 'insert')` = 2 because the previous run's rows are
append-only. The recipe is [`Database-Local.md`](../Specs/Database-Local.md:532) §10.1 and was
applied before the green run.
