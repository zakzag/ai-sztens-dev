# AIS-118 — admin `src/app/` layer

**Date:** 2026-10-30
**Ticket:** AIS-118 (subtask of AIS-105)
**Plan:** [`docs/plans/2026-10-30--17-25-00-ais-118-admin-app-layer-plan.md`](../plans/2026-10-30--17-25-00-ais-118-admin-app-layer-plan.md:1)

---

## 1. Problem / feature

The `react.coding-standards.md` prescribes an `src/app/` layer (providers, router, layout shell,
session, error boundary) for the React apps, but the admin SPA had none. Everything lived in
`apps/admin/src/App.tsx` (68 lines), which mixed four responsibilities:

| Responsibility                            | Lines        |
| ----------------------------------------- | ------------ |
| Auth provider                             | 61           |
| Route markup (6 `<Route>`)                | 48–53, 62–65 |
| Hand-written navigation list (2 `<Link>`) | 34–42        |
| Layout shell (header, `<main>`)           | 20–55        |

The route table and the navigation list were **two separate hand-written lists** — the exact
duplication that drifts. `UI-Architecture.md` §2 recorded the layer as "not created".

## 2. Measured data / evidence

Baseline before the change (Node 24.22.2, pnpm 9.15.4):

| Metric                   | Before                                                |
| ------------------------ | ----------------------------------------------------- |
| `App.tsx` size           | 68 lines                                              |
| admin test files / tests | 14 / 145                                              |
| route definitions        | 6 `<Route>` elements, 2 `<Link>` elements — two lists |
| new npm dependencies     | 0                                                     |

After:

| Metric                   | After                                                                |
| ------------------------ | -------------------------------------------------------------------- |
| `App.tsx` size           | **35 lines** (composition only)                                      |
| admin test files / tests | **20 / 173**                                                         |
| route definitions        | **1** registry list; `<Routes>` and the nav are both derived from it |
| new npm dependencies     | **0** (no `zustand` either)                                          |

Verification: `pnpm --filter @callback/admin test` → 20 files, 173 tests, 0 failures; `lint` → 0
errors; `build` → OK; the palette check over `apps/admin/src` and `packages/ui/src` → empty.

## 3. Root cause / design rationale

The layer was missing because the `App.tsx` was written as a single file and never split; the
architecture rule had no enforcement (the layer-lint gate is AIS-122, still open).

**The dependency order was inverted.** The ticket said the notification (AIS-84) and session
(AIS-74) stories build _on_ AIS-118, but the 2026-10-30 review reversed this in both tickets'
comments: _"the `src/app/` layer is created by AIS-118"_ (AIS-84) and _"the `src/app/session/`
layer is named by AIS-118"_ (AIS-74).

That left the ticket's own D2 in conflict — it said the session store is _only named here_, while
the AIS-74 comment said AIS-118 _creates the cookie session_. Since the cookie session also
rewrites `LoginPage.tsx`, taking it on would have made three tickets edit the same file.

**Resolution:** split structure from behaviour. AIS-118 creates the session **place**
(`useRequireSession`, a single hook the app layer reads) and AIS-74 implements the session
**behaviour** (cookie session, login page). The dependency cycle disappears, and the migration
becomes a one-file change.

Alternatives rejected:

| Alternative                                                       | Why not                                                                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Keep the nav list hand-written in the layout                      | The duplication the ticket exists to remove                                    |
| Write the cookie session here                                     | Three tickets would edit `LoginPage.tsx`; contradicts both dependency comments |
| Import the registry inside the components instead of injecting it | The components could not be tested with a minimal registry                     |
| Add a nav section structure now                                   | YAGNI — the rules prescribe a per-route label, not sections                    |

## 4. Solution / implementation

New `apps/admin/src/app/`:

| File                                                           | Change                                                                                             |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `router/route-registry.tsx`                                    | The single route table: `PUBLIC_ROUTE_ENTRIES`, `PROTECTED_ROUTE_ENTRIES`, `NOT_FOUND_ROUTE_ENTRY` |
| `router/route-entry.interface.ts`                              | The `RouteEntry` type (`path`, `navLabel`, `element`, `protected`, `hidden`)                       |
| `router/AppRouter.tsx`                                         | The `<Routes>` derived from the registry                                                           |
| `router/ProtectedRoute.tsx`                                    | The "is there a session?" decision — login page or layout                                          |
| `layout/AdminLayout.tsx`                                       | Header, nav and `<main>`; owns the frame, not the auth decision                                    |
| `layout/AdminNav.tsx`                                          | The navigation generated from the registry; `NavLink` supplies `aria-current`                      |
| `providers/AppProviders.tsx`                                   | The provider chain: `QueryClientProvider → SessionProvider`                                        |
| `providers/SessionProvider.tsx`                                | The session adapter over the existing `AuthContext`                                                |
| `session/use-require-session.ts`                               | The only hook that reads the session                                                               |
| `error/AppErrorBoundary.tsx`                                   | The React error boundary — a render error shows `PageErrorState`, not a white screen               |
| `app.const.ts`, `app.interface.ts`, the `*.interface.ts` files | Constants and types                                                                                |

Modified:

| File                            | Change                                                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `src/App.tsx`                   | Route markup, nav list and layout moved to the `app/` layer; now composition only                                                       |
| `src/main.tsx`                  | The `QueryClient` is created here and handed to `App` as a prop (the notification store must bind its cache callbacks to that instance) |
| `docs/Specs/UI-Architecture.md` | §2 layer table, new §4.1 (the `app/` layer) and §4.2 (adding a route), §5 state plan, §6 recipe step 6, header date                     |

New tests and mocks: `route-registry.test.ts`, `AdminNav.test.tsx`, `AdminLayout.test.tsx`,
`AppRouter.test.tsx`, `ProtectedRoute.test.tsx`, `AppErrorBoundary.test.tsx`, plus
`test/mocks/route-registry.mock.tsx` and `test/mocks/app-router.mock.tsx`.

**Not changed:** `auth/AuthContext.tsx`, `auth/session-token.ts`, `pages/LoginPage.tsx` (all
AIS-74's scope), `features/`, `entities/`, `packages/ui`, `packages/api-client`, every
`package.json`.

## 5. Outcome and how to verify

The admin SPA has the prescribed `src/app/` layer. `App.tsx` contains no route markup and no
navigation list. Adding a page is **one registry entry** — the link appears on its own.

```bash
pnpm --filter @callback/admin test    # 20 files, 173 tests
pnpm --filter @callback/admin lint    # 0 errors
pnpm --filter @callback/admin build   # OK
pnpm test                             # the whole matrix
```

Manual: start the dev server and open `http://localhost:5174/api-keys` — the shell renders with
the nav built from the registry, and the page loads. The dev proxy already forwards `^/api/` (not
the `/api` prefix), so the deep link returns the SPA shell; the registry test **enforces** that no
route may start with `/api/`.

## 6. Follow-ups

- **AIS-74** swaps the session implementation behind `useRequireSession` — one file.
- **AIS-84** adds `app/notifications/` and the `NotificationProvider` between the query client and
  the router; the `QueryClient` prop already exists for it.
- **AIS-122** (layer lint, knip, palette check) can now enforce the layer map — the `app/` layer
  it describes actually exists.
- **AIS-119** (URL list state) needs the route registry for the route-aware links.
- The `/calls` route is still a placeholder carried by the registry; the nav entry for it is
  inherited from the pre-AIS-118 behaviour, and the calls feature has no owner yet.
- The error boundary logs to the console; there is no error-reporting service yet.
