# AIS-122 — Four UI rules became machine gates

**Date:** 2026-11-02 · **Ticket:** AIS-122 (subtask of AIS-105) · **Plan:** `docs/plans/2026-11-02--18-25-00-ais-122-quality-gates-plan.md`

## 1. Problem / feature

[`react.coding-standards.md`](../../.roo/rules/react.coding-standards.md:1) declares the layer map
(§0.6, §1, §2) and the token rules (§7) non-negotiable, but nothing enforced them. A PR that
imported another page's store, wrote `bg-slate-800`, or branched on `error.code` inside JSX merged
green. The ticket turns four rules into CI gates: **layers**, **dead code**, **palette**,
**field errors**.

## 2. Measured starting point

| Area                                | Before                                                                                                   |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Layer enforcement                   | none — no dependency-cruiser, no eslint-plugin-boundaries, no knip in any `package.json`                 |
| `apps/web` palette                  | 18 offending lines in 5 files (`bg-slate-900/950`, `ring-slate-800`, `text-white/slate-200/400/500/100`) |
| `apps/admin`, `packages/ui` palette | already clean                                                                                            |
| Field-error rule                    | already clean (all comparisons already sat in `*.logic.ts` / `lib/error-message.ts`)                     |
| `knip` first run                    | 4 unused files, 21 unused exports, 2 unused devDependencies, 1 duplicate export                          |

## 3. Root cause / design rationale

Nothing was wrong with the code — the rules simply had no executor. Key decisions:

| #       | Decision                                                                                                                                 | Why                                                                                                          |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| D2      | **One rule module** (`.dependency-cruiser.rules.cjs`) imported by the real config **and** the fixture config                             | "the gate" and "the proof of the gate" cannot drift                                                          |
| D4      | Two documented grandfathers instead of a refactor: `components → features/error-surface` (AIS-96) and `auth` as its own element (AIS-74) | the gate had to be green on `main` on day one                                                                |
| D6      | Palette rule set = 3 rules; **only** `packages/ui/src/styles/theme.css` is exempt, and only from the literal rule                        | the exemption is one file, one rule — a palette utility there still fails                                    |
| D7      | `apps/web` migrated to tokens in this change                                                                                             | the alternative was a permanent exemption nobody removes                                                     |
| D8      | `knip` covers `apps/{admin,web}` + `packages/{ui,api-client,shared}`; `apps/api` excluded                                                | Nest DI resolves at runtime and `apps/api/drizzle/**` is generated; a gate that cries wolf gets switched off |
| D9      | Field-error allowlist = `lib/error-surface.logic.ts`, `lib/error-message.ts`, `**/*.logic.ts`                                            | the allowlist _is_ the rule: the decision belongs in a pure function                                         |
| D10/D11 | Separate `quality-gates` CI job, one step per gate; `pnpm quality` chains all four locally                                               | the red step names the failing gate; a developer runs one command                                            |

Two plan assumptions did not survive contact with `dependency-cruiser` and are recorded here:

- `enhancedResolveOptions.extensionAlias` is **not** in its config schema (`additionalProperties:
false`) — the whole config is rejected. Resolution of the repo's explicit `.js` specifiers works
  natively through `extensions: ['.ts', '.tsx', '.js']`.
- `options.tsConfig` was unusable: dependency-cruiser resolves the tsconfig's `extends` from the
  **cwd**, yielding `TS5083 Cannot read file …apps/admin/tsconfig.base.json` and `TS18003`. Neither
  admin tsconfig declares `paths`/`baseUrl`, so the option bought nothing.

## 5. Outcome and how to verify

All four gates are green on the branch, and each one is proven to **fire** — a gate that cannot fail
is not a gate. `apps/web` builds with token utilities in the emitted CSS.

```bash
pnpm install && pnpm --filter @callback/shared build
pnpm test:quality        # 39 tests: negative + positive fixtures, walker, reporter
pnpm quality             # layers → dead code → tokens → field errors, all exit 0
pnpm --filter @callback/web build
grep -c "bg-surface-raised" apps/web/dist/assets/*.css   # token utilities are emitted
pnpm test && pnpm -r lint && pnpm -r build
```

The CI proof: break a rule in a throwaway branch (e.g. `import { HomePage } from '../pages/HomePage.js'`
inside `apps/admin/src/pages/api-keys/ApiKeysPage.tsx`, or add `bg-slate-800` to an `apps/web/src`
component) — `quality:layers` / `quality:tokens` go red with `file:line: [rule]`, and revert turns
them green again.

### 5.1 pnpm settings migration (follow-up, same day)

`pnpm quality` first failed with `ERR_PNPM_VERIFY_DEPS_BEFORE_RUN` — "installing would drop
`pnpm.overrides` … because the `pnpm` field in package.json is no longer read by pnpm". Two causes,
both outside the gates:

1. `node_modules` had been installed by the shell's pnpm **9.15.4** (`node_modules/.modules.yaml`
   recorded `packageManager: pnpm@9.15.4`) while the repo pins **12.16.1** — pnpm 12 refuses to run
   scripts against a store written by another major.
2. `pnpm.overrides` still lived in `package.json`; pnpm ≥11 reads settings only from
   `pnpm-workspace.yaml` (which this repo already uses for `allowBuilds`).

Fix: move the override into `pnpm-workspace.yaml`, add `msw: false` to `allowBuilds` (pnpm 12 fails
on any _unlisted_ package with an install script), and re-install with the pinned pnpm 12. Afterwards
`pnpm install` is a no-op and `pnpm quality` / `pnpm test:quality` exit 0.

**Known, transient:** pnpm 12's default 24-hour `minimumReleaseAge` policy rejects four lockfile
entries published earlier the same day (`@tanstack/react-query`/`query-core@5.105.2`, `strtok3@10.7.0`,
`token-types@6.2.0`). The pre-run install prints `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` plus a
"node_modules may be out of sync" warning but the scripts still run and pass. Self-heals after
2026-11-03T13:54Z; a deliberate re-install before then needs `--config.minimumReleaseAge=0`. The repo
policy was **not** relaxed — that is an owner decision.
