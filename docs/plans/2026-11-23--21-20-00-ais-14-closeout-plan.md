## 5. R3 — the recorded decision (D1): `PATCH /:id` and the `422`

The AIS-14 DoD says `PATCH /:id` answers **`422` semantic error**. The implementation follows AIS-108, and
that is the right answer — so the **ticket text** changes, not the code.

| Situation on `PATCH /api/admin/customers/:id` | Answer | Where |
| --- | --- | --- |
| malformed body, unknown key, bad uuid | `400 VALIDATION_FAILED` + `details[]` | zod pipe |
| body valid, `updatedAt` is not the current version | `409 STALE_WRITE` + `details[{ path: 'updatedAt' }]` | repository guard |
| body valid, content impossible (e.g. a foreign `customerUserId`, `tagId`, `from > to`) | `422 SEMANTIC_VALIDATION_FAILED` | child-resource services |
| empty body, current token | `200`, silent no-op (AIS-108 `D7`) | service |

Deliverable — one short subsection appended to [`API-Convention.md`](../Specs/API-Convention.md:267) §4.3
plus the header date bump on line `5`:

> **`PATCH` never answers `422` for a shape or version problem.** A malformed body is `400`, a stale
> `updatedAt` is `409 STALE_WRITE`; `422 SEMANTIC_VALIDATION_FAILED` is reserved for a *well-formed* request
> whose content is impossible, and only the child resources of `customers` use it. The AIS-14 DoD wording
> ("`422` semantic error on `PATCH`") predates AIS-108 and is superseded by this section.

This is exactly the "one-off `422` branch" the gap analysis §M9 refused: adding it would make `customers` the
only resource in the API that answers that way, for no client benefit.

## 8. Decisions recorded by this plan

| Id | Decision | Rationale |
| --- | --- | --- |
| D1 | Keep AIS-108 (`400` shape / `409 STALE_WRITE` version / `422` content); fix the AIS-14 DoD text | A `422` on `PATCH /:id` would be a one-off in the whole API and would break the "retry advice stays correct" rule of AIS-108 |
| D2 | The five customer controllers keep injecting the **concrete** service class; `customers.service.interface.ts` is **not** added | The repository and the `AuditWriter` *are* behind interfaces/tokens, so the test seam already exists; the services are `@Injectable()` singletons with no alternate implementation, and introducing five interfaces + tokens days before the merge would be churn with no observable behaviour change. Recorded here so it reads as a decision, not an oversight (the gap analysis §4 flagged it) |
| D3 | Duplicate `customerNumber` stays unit-tested only | The value is generated from `customer.number_counters`, so a collision cannot be triggered through the public API without forging a counter row; the alternative (a test-only seam) would be dead production code. Tax number, second `owner` and second `primary` contact — the three cases that *are* reachable — are proven in e2e |
| D4 | The ledger has no write endpoint, no export and no full-text search | Append-only by construction; a search over `jsonb` payloads would promise a relevance the index cannot serve (slice-f `F6`/`F10`) |
