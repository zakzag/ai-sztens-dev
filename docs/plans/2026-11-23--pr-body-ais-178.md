## Design decisions worth reviewing

- **The database is the only place an invariant lives.** Partial/unique indexes and composite foreign
  keys carry the rules, and each is mapped to an honest answer instead of a `500`:
  `CUSTOMER_TAX_NUMBER_CONFLICT` (`409`), `CUSTOMER_PRIMARY_CONTACT_CONFLICT` (`409`, second
  `primary` contact), `CUSTOMER_OWNER_CONFLICT` (`409`, second `owner` customer user),
  `SEMANTIC_VALIDATION_FAILED` (`422`, a login user or contact belonging to another customer),
  `STALE_WRITE` (`409`, an outdated `updatedAt` token). No pre-check can be raced; the constraint
  decides.
- **Every write is one transaction with its own ledger row.** `audit.audit_logs` is append-only
  (triggers from migration `0007`), and `AuditWriter.write(input, tx, facts)` runs inside the business
  transaction, so a rollback cannot leave a lying audit row behind.
- **The ledger has no write path.** `customers-audit-logs.repository.ts` exposes `findPage` and
  nothing else, and the `0007` triggers refuse `UPDATE` / `DELETE` / `TRUNCATE` even for the table
  owner — "read-only" is enforced twice, in the module and in the database.
- **`updatedAt` is a token that is compared, never written.** `$onUpdate` maintains it; a `PATCH`
  sends it back, and a mismatch is `409`, not a silent overwrite. Where the row has no `updated_at`
  yet (a never-edited activity) the token is `coalesce(updated_at, created_at)`.
- **Delete of a contact writes two ledger rows**: `contact_roles` `delete` (`recordId: null`, the
  removed set in `before`) and `contacts` `soft_delete`. Roles are hard-deleted on purpose — the table
  has no `deleted_at`, and a soft-deleted role would keep the `primary` slot occupied forever.
- **Roles are part of the contact payload and are replaced as a set.** "Move the primary flag" is one
  request, and the replace is atomic.
- **The tag POST is create-or-attach, the PATCH is attach-only.** Attaching an existing name must not
  silently create a near-duplicate tag.
- **The AIS-110 client gate is satisfied without a second service.** All 21 operations are registered
  under `customers.*`, so their methods live on the existing `CustomersService`.
- **One new shared helper**: `toListQueryParams` is now generic, because the previous version silently
  dropped every resource filter (`status`, `country`, `tagId`, and later the tag/user filters) that
  was not a paging field.
- **Two SQL-reference helpers exist because Drizzle's raw `sql` is untyped at the boundary.**
  `qualifiedColumn()` (`apps/api/src/db/sql-reference.ts`) renders `"schema"."table"."column"` from the
  schema metadata, and a raw `sql` parameter that carries a `Date` is formatted to ISO text first
  (a raw parameter skips the column encoder). Both are consequences of defects this PR fixes — see
  below.

## Defects found by the close-out gate sweep (fixed here)

The full sweep (`closeout plan` §3) ran on this branch for the first time and found five real
problems, all fixed in this PR:

| Defect | Fix |
| --- | --- |
| `GET /customers` answered `500` — `42702 ambiguous column reference` in the derived subqueries | `qualifiedColumn()` + a spec that asserts the projection stays qualified |
| `GET /customers/:id` answered `500` — `value.toISOString is not a function` (a derived column arrives as text) | `toNullableIsoString` accepts `Date \| string \| null` and throws on anything else |
| `statusChangedAt` was 2 ms after `createdAt` on a fresh row | the insert leaves both to the database's `now()` |
| `PATCH …/activities/:id` answered `500` — `ERR_INVALID_ARG_TYPE … Received an instance of Date` | the token is bound as ISO text with `::timestamptz` |
| a 5xx log line named the statement but not the reason | `ApiExceptionFilter` appends the `cause` chain to a 5xx line |
