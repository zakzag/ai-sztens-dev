## What this PR adds

The `customers` resource of the admin back office, end to end: database schema, shared contract, NestJS
API with audit, typed client, and the Hungarian rejection copy. It is the first `/api/admin/*` family and
therefore also the reference implementation for the ones that follow.

Nothing in the admin UI changes here — the screens are **AIS-179**.

## Endpoints

| Method | Route | Answer |
| --- | --- | --- |
| `GET` | `/api/admin/customers` | paged list; filters `q`, `status`, `country`, `tagId`, sort/order |

| `GET` | `/api/admin/customers/:id` | detail incl. `tags`, `contacts[].roles`, `customerUsers` |

| `PATCH` | `/api/admin/customers/:id/status` | writes `status` **and** `statusChangedAt` |
| `DELETE` | `/api/admin/customers/:id` | soft delete, tax number freed for reuse |

| `POST` | `/api/admin/customers/:id/contacts` | `201` |

| `DELETE` | `/api/admin/customers/:id/contacts/:contactId` | soft delete + hard delete of the roles |

## Design decisions worth reviewing

- **The database is the only place an invariant lives.** Three partial/unique indexes and two composite
  foreign keys carry the rules, and each is mapped to an honest answer instead of a `500`:
  `CUSTOMER_TAX_NUMBER_CONFLICT` (`409`), `CUSTOMER_PRIMARY_CONTACT_CONFLICT` (`409`, the second
  `primary` contact), `SEMANTIC_VALIDATION_FAILED` (`422`, a login user belonging to another customer),
  `STALE_WRITE` (`409`, an outdated `updatedAt` token). No pre-check can be raced; the constraint decides.
- **Every write is one transaction with its own ledger row.** `audit.audit_logs` is append-only
  (triggers from migration 0007), and `AuditWriter.write(input, tx, facts)` runs inside the business
  transaction, so a rollback cannot leave a lying audit row behind.
- **`updatedAt` is a token that is compared, never written.** `$onUpdate` maintains it; a `PATCH` sends
  it back, and a mismatch is a `409`, not a silent overwrite.
- **Delete of a contact writes two ledger rows**: `contact_roles` `delete` (`recordId: null`, the removed
  set in `before`) and `contacts` `soft_delete`. Roles are hard-deleted on purpose — the table has no
  `deleted_at`, and a soft-deleted role would keep the `primary` slot occupied forever.
- **Roles are part of the contact payload and are replaced as a set.** "Move the primary flag" is one
  request, and the replace is atomic. A roles-only `PATCH` does not bump `contacts.updated_at` (the roles
  live in their own table); the token is still verified, so a stale client still gets `409`.
- **The AIS-110 client gate is satisfied without a second service.** The four contact operations are
  registered under `customers.*`, so their methods live on the existing `CustomersService`.
- **One new shared helper**: `toListQueryParams` is now generic, because the previous version silently
  dropped every resource filter (`status`, `country`, `tagId`) that was not a paging field.

**The SQL assertions run in CI, not locally.** The persistence e2e suites self-skip when `DATABASE_URL` is
unset, so on a laptop without Postgres they only prove that the app compiles and boots. The
`API e2e (envelope + OpenAPI gates, Postgres)` job in `ci.yml` starts `postgres:16-alpine`, applies the
migrations and runs `pnpm --filter @callback/api test:e2e` against it — that is the run which actually
exercises the constraints above, including `customer-contacts.e2e-spec.ts`.
